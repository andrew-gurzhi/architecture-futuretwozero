## Целевая архитектура

В целевой архитектуре компания «Будущее 2.0» переходит от централизованного DWH к доменно-ориентированной архитектуре с
использованием Data Platform.

Ключевые изменения:

- Разделение системы на домены: медицинский, финтех, AI.
- Отказ от DWH как центрального элемента хранения и обработки данных.
- Внедрение Data Platform (Data Lake/Lakehouse) для аналитики.
- Переход к событийной архитектуре (Kafka) вместо ESB.
- Реализация self-service портала для аналитики.

### Поддержка бизнес-сценариев

**1. Быстрая подготовка отчетности**
Данные поступают из доменов в Data Lake через Event Streaming. Обработка выполняется асинхронно, что позволяет
значительно сократить время формирования отчетов.

**2. Независимое развитие доменов**
Каждый домен (медицина, финтех, AI) имеет собственные сервисы и базы данных, что позволяет развивать их независимо.

**3. Масштабирование под новые бизнесы**
Новые домены могут подключаться к платформе через публикацию событий без изменений в существующих системах.

**4. Безопасность медицинских данных**
Чувствительные медицинские данные хранятся отдельно и не попадают в аналитическую витрину. Для аналитики используются
только агрегированные или обезличенные данные.

## Проблемы текущей архитектуры

| Проблема                      | Описание                                        | Влияние на бизнес                      |
|-------------------------------|-------------------------------------------------|----------------------------------------|
| Монолитный DWH                | Вся логика и данные сосредоточены в одном месте | Замедляет развитие и масштабирование   |
| Медленная отчетность          | Отчеты формируются часами                       | Замедление принятия решений            |
| Сильная связанность через ESB | Все интеграции проходят через одну шину         | Снижение отказоустойчивости и гибкости |
| Устаревшие технологии         | SQL Server 2008, PowerBuilder                   | Сложности поддержки и развития         |
| Отсутствие доменной изоляции  | Медицинские и финансовые данные смешаны         | Ограничение независимости команд       |
| Зависимость BI от DWH         | BI напрямую работает с DWH                      | Любые изменения влияют на отчеты       |
| Ограниченная масштабируемость | Система не справляется с ростом данных          | Ограничение роста бизнеса              |
|                               |                                                 |                                        |

## Миграция с DWH на Data Lakehouse

Переход выполняется постепенно, без остановки текущей системы.

1. Сначала разворачивается Data Lakehouse параллельно с DWH.  
2. Настраивается перенос данных из DWH.  
3. Новая отчетность начинает строиться уже в Data Lakehouse.  
4. Логика трансформаций постепенно переносится из DWH в отдельный слой обработки (Spark/Flink).  
5. После переноса всех сценариев DWH теряет роль центра системы и может быть выведен из эксплуатации.

---

## Миграция с ESB на Event-driven архитектуру

Переход также выполняется постепенно, с переносом логики из ESB в новые компоненты.

### Что происходит с логикой ESB

- Маршрутизация → заменяется на события (Kafka), сервисы сами подписываются на нужные данные  
- Трансформации → переносятся в слой обработки данных (stream processing)  
- Валидации (ФЛК) → выполняются внутри доменных сервисов  
- Интеграции → делятся на:
  - синхронные (через API)
  - асинхронные (через события)

### Как проходит переход

1. Kafka запускается параллельно с ESB  
2. Новые интеграции сразу делаются через события  
3. Старые постепенно переписываются  
4. После этого ESB можно отключить

## Приоритизация проблем (MoSCoW)

### MUST HAVE (критично)

- Разделение системы на домены
- Уход от DWH как центра системы
- Внедрение Data Platform

**Обоснование:** напрямую влияет на скорость разработки, масштабируемость и time-to-market.

---

### SHOULD HAVE (важно)

- Переход с ESB на event-driven архитектуру
- Внедрение self-service витрины данных

**Обоснование:** 
улучшает гибкость и скорость аналитики.

---

### COULD HAVE (желательно)

- Миграция BI-системы
- Обновление пользовательских интерфейсов

**Обоснование:**
улучшает пользовательский опыт, но не критично для ядра системы.

---

### WON’T HAVE (пока не делаем)

- Полный отказ от легаси-систем одномоментно

**Обоснование:**
высокий риск и стоимость, целесообразен постепенный переход.
